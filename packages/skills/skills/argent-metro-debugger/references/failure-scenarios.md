# Failure Scenarios: Recovery Steps

When a debugger tool fails, use **`debugger-status`** first to diagnose. Note: `debugger-status` and `debugger-log-registry` do **not** fail when the debugger is simply unreachable — they return `{ status: "not_connected", reason, detail, guidance }` (the `detail` field carries the same error text other tools throw), and `debugger-log-registry`'s answer may add a `note` about the console history a dead session left. Match the error, `reason`, or situation below and act as specified. Do not retry the same failing tool repeatedly without following the recovery steps.

| Scenario                           | Error or situation                                                                                                                                 | What to do                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Metro not running**              | Error (or `not_connected` `detail`) contains: `Metro at port 8081 is not running (got: ...)`                                                       | `debugger-status` / `debugger-log-registry` return `{ status: "not_connected", reason: "metro_not_running", guidance }` here instead of erroring; other debugger tools still throw. **Start Metro yourself** unless the user asked you not to: scan the workspace configuration and run the appropriate command to start Metro in the background (by default `npx react-native start` or `npx expo start`). Wait for Metro to be ready, then retry `debugger-connect` or `debugger-status` once — not in a loop. If you cannot determine the project root, ask the user. A non-Metro server occupying the port lands here too — the `got:` text shows what answered.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **No source locations**            | `projectRoot` is `""` and source lookups report no file:line                                                                                       | Not a failure. Legacy Metro (RN 0.72 and older, e.g. Vega) sends no `X-React-Native-Project-Root` header, so paths cannot be resolved against a project root. `debugger-evaluate`, console logs and the network inspector work regardless — do not restart Metro to "fix" it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **App not connected**              | Error (or `not_connected` `detail`) contains: `Metro at port 8081 has no CDP targets — is a React Native app connected?`                           | `debugger-status` / `debugger-log-registry` return `{ status: "not_connected", reason: "no_app_connected", guidance }` here instead of erroring; other debugger tools still throw. 1) Confirm the app is running on the device. 2) If an app was connected and has since died, read `debugger-log-registry`'s `note`: when that session left a log file the note names it. Call that tool if you got here from `debugger-status`; if this answer IS `debugger-log-registry`'s, its `guidance` says outright whether it carried one. The file outlives the relaunch; the note is what gets spent, so read it here, or call `debugger-connect` after the relaunch to take it from there — `debugger-status`, which step 5 retries, never carries one. 3) Use `restart-app` with the app's device id and bundleId to relaunch so it connects to Metro. 4) Wait a few seconds for the bundle to load. 5) Retry `debugger-status` once. Do **not** use `debugger-reload-metro` to fix this — it also requires at least one target.                                                                                  |

Re-target with the `logicalDeviceId` listed in the `detail` / error message, or give the device its own Metro port. Do not retry with the same `device_id` — the result will not change.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Stale connection**               | `debugger-status` returns `reason: "stale_connection"`                                                                                             | The cached debugger connection was no longer open; `debugger-status` has already discarded it. That discard keeps the session's log file, so if it had captured anything, `debugger-log-registry` or `debugger-connect` returns a `note` naming it — read that before you go further. Use `restart-app` if the app is not running, then call `debugger-connect` — the next call reconnects fresh.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

Transient: wait a moment and retry once. Do **not** restart the app for this.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Runtime unresponsive**           | `reason: "runtime_unresponsive"`, or another debugger tool fails with `DEBUGGER_CDP_REQUEST_TIMEOUT`                                               | Follow the `guidance` / error text — it explains the state and the recovery. Each attempt waits out the full CDP timeout, so never retry in a loop.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **CDP endpoint unreachable**       | `debugger-status` / `debugger-log-registry` return `reason: "cdp_unreachable"`                                                                     | The runtime's CDP endpoint did not answer. On Chromium this is what a crashed renderer reads as, so read `debugger-log-registry`'s `note` first — it names the log file that session kept — then relaunch: `boot-device` with `electronAppPath` for an Electron app, or restart the browser with `--remote-debugging-port`. On Metro, confirm the app is running (`launch-app` / `restart-app`) and call `debugger-connect`, then retry once.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Was connected, then tool fails** | Any debugger tool fails with a connection or disconnect error after it was working                                                                 | The app may have crashed or been closed. A session whose runtime died holding console logs keeps its log file: call `debugger-log-registry` **first** and read the `note` in the answer — it names the file the dead session left, which is where the pre-crash output is, and see **Reading the note** below before you relaunch. Then relaunch the app — `restart-app` on iOS / Android / Vega, or `boot-device` with `electronAppPath` for a Chromium target, which `restart-app` declares no platform for — and call `debugger-connect` again; if nothing read the note earlier, that connect answer carries it, but only for a runtime that went away, and on Chromium only if the relaunch kept the same CDP port - the record is filed under the device id, which is that port, and `boot-device` picks a free one unless you pass `electronPort`. A session someone else tore down is spent there in silence, and that teardown deleted its file anyway. **If you connected with a `logicalDeviceId`** (which `debugger-connect` asks for once two devices share a port), reconnect with that same id. |

## Reading the note

A crashed session's console log is named by the `note` `debugger-log-registry` and `debugger-connect` hand out, and the first read spends it. The file itself outlives the note: kept logs sit in `~/.argent/tmp` as `argent-logs-<port>-<start-ms>.log` until a debugger session finds them a day old, so if the record was already spent, list that directory and grep the newest file whose timestamp predates the relaunch. The name carries the Metro port and a start time and nothing else, so where two devices shared that port it cannot tell their logs apart — check the contents before believing one is the crashed app's.

- **Read it before relaunching.** The next crash on this device and Metro port can reclaim the kept file of the one before it.
- **The answer may still carry the dead session's own entries**, if the teardown has not landed yet — then just read `file`.
- **No note usually means that session logged nothing** — the record is filed only for a session that ended holding console history. Whoever reads it first spends it, so a concurrent agent's `debugger-connect` may have taken it — and the record is per Metro port, so ask with the port that session used. On `reason: "reconnecting"` it means neither: the record is held for the retry that guidance asks for, so ask again before concluding anything.
- **A note saying no log file was left behind** (an explicit teardown deletes it), **or that a kept one has since been reclaimed**, means that session's entries are gone. It says nothing about an EARLIER session on the same device: a crash before this one can have left a file that no note names any more, so fall back to the listing this section opens with before concluding the output is unrecoverable.
- **Once the app is back and logging**, `debugger-log-registry` reports the new session instead, and the note moves to the next `debugger-connect`. That connect reports one only for an app that died on its own; a session someone else tore down is consumed there in silence.
- **The relaunch does not reissue the ids.** The app derives its `logicalDeviceId` from the device and the bundle, so Metro echoes back the same one and a record filed under it stays reachable. Keep reconnecting with the `device_id` the connect accepted; switch to the `logicalDeviceId` only where `reason: "device_mismatch"` tells you to, since connecting with it when nothing refused your id opens a second debugger session, with its own log file, for one device. Where two devices shared the port and one died, the survivor answers to the dead one's id — one target left is one `selectTarget` stops disambiguating — so check `deviceName` and `appName` in the connect answer before trusting that the app you lost is the one that came back.
