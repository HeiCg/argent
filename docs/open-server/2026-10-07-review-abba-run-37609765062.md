## Part A — PROBE-BG, transition timeline, P5

1. NOTE — the log verdict `on-at-spawn` holds. Window B only does
   `resolveService` + 2 s sleep (`bench-open-vs-proprietary.ts:3776-3781`);
   the Android factory checks adb, spawns `simulator-server android --id
<serial>` with the inherited env and runs an iOS-only foldable probe
   (`blueprints/simulator-server.ts:147, 557-616, 318-330`), identical to
   upstream/main. Only extra env in the probe: debug log level. "Requesting
   screenshot stream" / "Starting GRPC stream receiver" at 10:58:42, before
   "API server started" (`bench-log-PROBE-BG.txt`). The stream is part of the
   binary's startup, with no client.
2. MAJOR — the probe's −24.2 / −36.2 pp CPU deltas are noise and must leave
   the verdict text. CPU-seconds per window: A 59.3, B 54.2, C 51.1, A2 51.3.
   A is the outlier: first window, 3 s after `am start`, load sampler shows
   qemu climbing 86 → 346 %. B, C, A2 within ±6 %. The baseline averages A
   and A2 (`:3801-3810`), so A's warm-up becomes the "delta". Real ΔCPU ≈ 0
   with ±43 pp noise. At qemu 290-345 % on 4 cores the CPU is saturated:
   extra work shows as a slower guest, not higher CPU. The only signal in the
   stream's favour is adb command time per window (duration − 11.2 s sleep):
   A 6.0, B 6.9, C 6.6, A2 5.8 s, +10-15 % with the server alive, n=1. MINOR:
   the table shows 0 stream lines in B because they arrive before sampling
   starts (`:3750`); `firstStreamLineWindow` is right, the table reads as a
   contradiction.
3. MAJOR — the guest IS more loaded in OFF, cause not shown. Time-weighted
   qemu CPU from `load-samples.jsonl`: OFF-1/2/3 292.5 / 291.6 / 290.0 %;
   ON-im-1/2/3 249.7 / 246.6 / 246.7; ON-uia 244.6; OFF-legacy 286.8. OFF
   +44 pp (+17.7 %), <3 pp spread within each arm. simulator-server 0.8-0.9 %
   in OFF, never alive in ON. On-device `com.argent.*` 1.1 % in OFF vs
   3.7-3.9 % in ON: our server costs more in the guest and the guest is still
   faster. Inference: the extra work is in the host qemu process (frame reads
   for the stream under software GPU). Against: in the gesture-tap phase,
   where the 717 vs 370 ms gap lives, qemu is at parity (OFF 328-330, ON-im
   317-348; `scoreboard.md:462-517`). Not measured: vCPU vs emulator threads
   (`/proc/<qemu>/task/*/stat`), host idle/steal.
4. NOTE (strong) — t0 is equivalent and the tap reaches the guest at the
   same instant on both arms. Launcher `TaplEvents` from the marker, p50:
   touch starts 4-5 ms, ends 54-55 ms, touch end → START 40-50 (OFF) vs
   34-40 (ON); START → onCreate OFF 161/214/186 vs ON 84/74/78; onCreate →
   Displayed OFF 392/398/386 vs ON 196/198/192. The whole difference is in
   the guest after the touch: SubSettings opens and draws ~2× slower. The
   "tap arrives late on OFF" hypothesis is refuted. The marker is written
   before t0 on both arms (`:1115-1117`). The harness's `dumpsys activity`
   poll every 150 ms (`:1139-1144, :2311`) lands ~0.7× per tap inside the
   transition on both arms and never in the P5 verb; OFF stays 2× slower
   there (669/587/601 vs 358/338/348), so the poll is not the cause.
5. BLOCKER for the label "driver win"; the arithmetic is right. P5
   decomposition, mean of block p50s, OFF → ON-im:

   | component                                                           | OFF → ON-im | Δ     | share |
   | ------------------------------------------------------------------- | ----------- | ----- | ----- |
   | time-to-correct (`scoreboard.md:625`)                               | 2621 → 1457 | −1165 | 100 % |
   | tap → transition finished, in the guest (`:543-598`)                | 1224 → 560  | −664  | ~57 % |
   | after the transition (await + describe)                             | 1412 → 939  | −473  | ~40 % |
   | ↳ await floor on a still screen: algorithm, not driver (`:82, :90`) | 497 → 302   | −195  | ~17 % |
   | ↳ describe                                                          | 52 → 44     | −8    | <1 %  |
   | ↳ unattributed                                                      | 863 → 593   | −270  | ~23 % |

   No run crossed the await algorithms (ON with the host await, or OFF with
   the on-device await), so algorithm vs driver was not measured. Driver
   tool speed (tap 53 ms both, describe −8 ms) explains ≤1 % of Δ.

6. MAJOR — the stream is not proven to cause the 2×. Proven: stream on at
   spawn; OFF guest 2× slower to open and draw with the touch arriving at the
   same time. Not excluded: the proprietary helper `com.argent.androiddevtools`
   (accessibility / UiAutomation setup) or any other OFF component. Only
   evidence isolating the stream: the +10-15 % adb time, n=1. Resolving test:
   an arm `ON-im + simulator-server idle` (spawned, no calls) inside the ABBA.
   If tap → first frame goes from ~370 to ~700 ms, the stream is the cause.
   Alongside: sample `/proc/<qemu>/task/*/stat` (vCPU vs emulator threads)
   and host `/proc/stat`.
7. MAJOR (scope) — environment-bound. swiftshader_indirect, 4 cores, qemu
   250-370 %. `ci-runner-env.json` already says "NOT comparable to local
   arm64/HVF". With a host GPU and more cores the −664 ms may shrink. Any

8. MINOR — block order: OFF always right before ON-im in the 3 pairs. No
   drift (first frame OFF 717/712/655, ON 370/366/362; qemu OFF 292/292/290).

9. MINOR — OFF-legacy (0.22.1) does not isolate the stream: same proprietary

10. NOTE — "after the transition" mixes clocks (host time-to-correct minus

Part A verdict: P5 is a stack-level end-to-end win in this CI (−1165 ms, ≥74 %
of it from the slower guest under the proprietary stack plus the await
algorithm). It is NOT a driver win until two new arms run: `ON-im +
simulator-server idle` (stream causality) and a crossed-await arm (algorithm
vs driver). The probe's −24/−36 pp must leave the verdict text.

## Part B — P11 empties, settle, P12

Read class by where the describe ENDS relative to the destination's first
frame (ff) and transition finished (fin), all tap+describe variants:

| arm   | ends before ff       | ends between ff and fin | ends after fin      |
| ----- | -------------------- | ----------------------- | ------------------- |
| OFF   | 97/97 pre-transition | 22/24 empty             | –                   |
| ON-im | 43/43 pre-transition | 15/18 empty             | 33 correct, 8 empty |

1. MAJOR (gate design) — P11 measures WHEN the read lands, not how good it
   is. ON settle:false is not slower (p50 263/411/228 vs OFF 438/313/327 ms);
   ON's first frame is earlier (332-358 vs 537-729 ms; finish 566-695 vs
   1154-1373), so the describe lands inside the transition, where the trimmed
   tree has 0 elements. OFF lands before the frame and returns the old screen
   silently. Both are wrong: settle:false correct-at-first-read ON 0/60, OFF
   2/60. P11 penalises ON for turning a silent error into a visible one.
   ON-im-2 9/20 has Wilson [25.8, 65.8] %, failing 25 % by 0.8 pt at n=20.
   Fix: grade P11 on wrong reads (empty + pre-transition), or apply it only to
   settle:true and await-idle. As run, P11 is not a product regression.
2. NOTE — the empty definition is the same on both arms:
   `bench-open-vs-proprietary.ts:260-266` counts `treeEmpty === true ||
elements === 0`, elements = lines under `ROOT` (`:507-521`). The server
   `treeEmpty` flag never fired (`openServerEmptyTreeCount = 0` in all 4 ON
   blocks; every empty line is `treeEmpty=false elements=0`). That flag only
   means "no active window after 10 retries 50 ms apart"
   (`StateHandler.kt:189-194, 344-347`, `ActiveRootRetry.kt:22-24`). Every
   empty on both arms is "root present, 0 elements after trim". Inference,
   not verified on device: the trim drops zero-area / off-screen nodes
   mid-animation (`open-server-tree.ts:71-73`).
3. MAJOR (product) — `settle:true` is a fixed 500 ms cap, not a quiet-screen
   wait. It becomes `waitTimeoutMs: 500` (`android/index.ts:56-63, 130`) →
   `uiDevice.waitForIdle(500)` (`StateHandler.kt:147`). UiAutomator's idle is
   500 ms with no accessibility event, capped at 500 ms (AndroidX constant
   recalled from memory; the logs below support it). After a tap that emits
   events the quiet window can never complete before the cap. Correct reads:
   50/51 (ON-im + ON-uia) hit `QueryController: Could not detect idle state.`
   at ~560-650 ms — the wait never saw a quiet screen. Pre-transition reads:
   16/16 had no timeout line; the wait returned before the tap's first event,
   first frame at 637-751 ms. Empty reads: 5/8 hit the cap at 564-618 ms with
   the transition finishing at 602-687; 3 returned early. ON-im-1 5/20 vs
   ON-im-2 0/20 empties is category drift, not a fix: non-correct reads were
   10/20, 7/20, 2/20; transitions finishing after 600 ms were 9/17, 9/16,
   4/18. Docs are wrong: "500 ms idle-quiescence window" at
   `describe/index.ts:92` and `android/index.ts:54` describes something the
   code does not do.
4. MINOR — where the ~826 ms of settle:true goes: ~57 ms marker → server
   (60/60 settle:false samples), 500 ms cap (times out), tree capture p50
   ~215 ms (138-321) while the app is still busy right after the transition
   (31-42 ms when the read lands well after it; idle describe 41-48 ms).
   Cutting the 500 does not work: the transition finishes 515-583 ms after
   describe starts, so a shorter cap means more empties. Saving would come
   from gating on accessibility events: `TreeStore.settleAfterAction`
   (`TreeStore.kt:262-275, 305-328`; `JsonRpcHandler.kt:240-247`, quiet
   window 80 ms) already does that. Rough estimate 150-250 ms, not measured.
5. MINOR (product) — the empty-tree hint is only added when the server
   reports no windows at all (`android/index.ts:146-147, 211-216`). A root
   with 0 elements reaches the agent with no hint.
6. NOTE — mostly a bench artifact. In the bench, describe reaches the server
   ~57 ms after the tap; in an agent loop a model turn sits between the two
   calls (≥1 s, inference), and ON transitions finish by 942 ms worst case.
   Plain `describe` was empty 0/150 on ON and 0/150 on OFF;
   `tap+await-idle+describe` was never empty and 40/40 correct per block. Real
   exposure: callers that run tap then describe back to back (flows, batch);
   not checked.
7. NOTE (retry data) — after an empty read, the next non-empty read was
   already the destination in 26/26 ON and 8/8 OFF settle:false samples. ON
   gap after the empty p50 265-433 ms; tap → correct for those samples p50
   779-865 ms, about the same as settle:true. A retry does nothing for
   pre-transition reads (time-to-correct 863-1054 ms, 1-3 polls).

Part B recommendation. (a) Default `settle:true`: no — back to back it still
gives 16/75 stale and 8/75 empty, and on a screen that keeps animating it
would likely add 500 ms to every describe (inference). (b) Retry on 0
elements: at most 2 reads 50 ms apart; 26/26 empties became correct on the
next read; cost ~+330 ms only on empty reads, up to ~500 ms on a genuinely
blank screen; does not fix the 37/60 silently stale reads. (c) Keep and
document: acceptable for the normal agent loop. Pick (c) + (b) + the hint of
finding 5 now; re-grade P11 per finding 1; then move settle to the action.

Architecture: settle belongs to the action, not the read. Let `tap` (and
swipe / key) optionally return after the first accessibility event (≤600 ms)
and a quiet window (80 ms, `settleAfterAction` already exists), capped at
~1500 ms. That removes the 16 stale reads where the wait returned before any
event and the 8 empties where the cap expired mid-transition. Keep `describe`
as an immediate read with retry-on-empty and a hint. Grade the bench on
correct-first-read and wrong-read rate, not on empty rate alone.

Not answered: why the trimmed tree has 0 elements mid-transition (bounds vs
visibility) — not checked on a device; whether an 80 ms quiet window lands
after the transition finishes — not measured; flows/batch exposure to
back-to-back tap→describe — not checked; OFF has no server-side idle log, its
read moment comes only from host latency.
